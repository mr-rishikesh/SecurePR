# DevInsight (SecurePR) — Deep Architectural & Module-by-Module Technical Specification

## System Architecture & End-to-End Execution Flow

DevInsight is an automated, AI-powered Pull Request security auditing system designed to process GitHub webhooks, audit incoming code changes against key threat vectors using Large Language Models (LLMs), record security telemetry, and report actionable findings back onto GitHub PR discussion threads.

```
┌─────────────────┐       HMAC-SHA256       ┌────────────────────────┐
│   GitHub Web    ├────────────────────────►│  app/api/webhook/      │
│   Repository    │    POST /api/webhook    │  route.ts              │
└────────┬────────┘                         └───────────┬────────────┘
         │                                              │
         │ Comment Posted                               │ Enqueue Job
         ▼                                              ▼
┌─────────────────┐  Octokit REST   ┌────────────────────────────────┐
│  PR Thread      │◄────────────────┤ Background Worker              │
│  Discussion     │                 │ (lib/worker.ts / worker.mjs)   │
└─────────────────┘                 └─────┬──────────────────┬───────┘
                                          │                  │
                           LLM Audit Diff │                  │ Store Audit Log
                                          ▼                  ▼
                            ┌───────────────────┐  ┌─────────────────┐
                            │ Groq API          │  │ Database Layer  │
                            │ (llama-3.3-70b)   │  │ (lib/db.ts)     │
                            └───────────────────┘  └────────┬────────┘
                                                            │
                                                            ▼
                                                   ┌─────────────────┐
                                                   │ Dashboard API & │
                                                   │ Next.js UI      │
                                                   └─────────────────┘
```

### End-to-End Processing Lifecycle:
1. **Event Trigger**: A developer opens, updates, or reopens a Pull Request on a GitHub repository configured with the DevInsight webhook URL.
2. **Webhook Receipt & Verification**: GitHub sends an HTTP POST request to `/api/webhook`. Next.js receives the request, verifies the cryptographic HMAC-SHA256 signature using `WEBHOOK_SECRET` in constant time, and extracts metadata.
3. **Async Queueing**: The webhook handler pushes a job containing PR parameters to a BullMQ queue backed by Redis (`pr-review`) and immediately responds to GitHub with `200 OK` in under 50ms. If Redis is offline, it falls back to non-blocking in-memory local processing.
4. **Worker Orchestration**: A background worker process (`lib/worker.ts` / `worker.mjs`) picks up the job, retrieves the unified git diff from the GitHub API via Octokit, and prepares the prompt payload.
5. **AI Threat Audit**: The worker sends the diff to Groq (`llama-3.3-70b-versatile`) via `lib/gemini.ts`, evaluating it against 7 security threat classes.
6. **Result Parsing & Telemetry**: The markdown report generated by the LLM is parsed into structured findings (counts, severity ratings, bug classifications) and stored in the database layer (`lib/db.ts` - Redis or local fallback JSON).
7. **Thread Posting**: The audit output is posted as a markdown comment on the GitHub PR thread.
8. **Dashboard Analytics**: The Next.js frontend fetches real-time aggregated security metrics from `/api/dashboard` and displays regional analytics.

## Module 1: Webhook Ingestion Engine
**File Path**: [`app/api/webhook/route.ts`](file:///c:/Projects/secure-pr/app/api/webhook/route.ts)

### 1.1 Why It Is Used
The Webhook Ingestion Engine acts as the entry point for all external events sent by GitHub. GitHub expects webhook endpoints to respond within 10 seconds (ideally under a few hundred milliseconds). Performing code analysis and LLM calls synchronously during the HTTP request would result in HTTP gateway timeouts and dropped webhooks. This module validates incoming security payloads, handles ping/non-PR events, enqueues work asynchronously, and responds in under 50ms.

### 1.2 How It Works Internally

#### HMAC-SHA256 Signature Verification
To prevent spoofing or unauthorized payload submissions, GitHub signs every request body using an HMAC SHA-256 hash key provided in `WEBHOOK_SECRET`. 

```typescript
function verifySignature(payload: string, signature: string, secret: string): boolean {
  const hmac = crypto.createHmac('sha256', secret);
  hmac.update(payload, 'utf8');
  const digest = `sha256=${hmac.digest('hex')}`;
  try {
    const a = Buffer.from(digest, 'utf8');
    const b = Buffer.from(signature, 'utf8');
    if (a.length !== b.length) return false;
    return crypto.timingSafeEqual(a, b);
  } catch {
    return false;
  }
}
```
* **Constant-Time Comparison**: Simple string comparison (`digest === signature`) is vulnerable to side-channel timing attacks. The engine uses `crypto.timingSafeEqual`, which compares byte buffer lengths first and then evaluates each byte in constant time regardless of match failure points.

#### Event & Action Filtering
GitHub sends webhooks for various actions (e.g. issues, star events, PR labels, PR closed). The route short-circuits execution early:
- `x-github-event === 'ping'`: Responds immediately with `{ ok: true, message: 'pong' }`.
- `x-github-event !== 'pull_request'`: Returns `{ ok: true, skipped: true }`.
- `action` not in `Set(['opened', 'synchronize', 'reopened'])`: Ignores non-code changes (e.g. PR assigned or closed).

#### Idempotency & Queue Fallback Mechanics
```typescript
const isRedisOnline = redisConnection.status === 'ready';

if (isRedisOnline) {
  // Use deliveryId as jobId — GitHub retries the same delivery ID, so this is idempotent
  await prReviewQueue.add('review-pr', jobPayload, { jobId: deliveryId });
} else {
  // Fallback: process job locally in-memory asynchronously since Redis is offline
  console.log(`Redis is offline. Processing delivery ${deliveryId} locally...`);
  import('@/lib/worker').then(({ processJobLocal }) => {
    processJobLocal(jobPayload).catch((err) => {
      console.error('Local worker processing error:', err.message);
    });
  });
}
```
- **Idempotency**: GitHub passes a unique `x-github-delivery` UUID header with each request. When enqueueing to BullMQ, `jobId: deliveryId` is set. If GitHub retries the same request due to a transient network issue, BullMQ deduplicates the job automatically.
- **Graceful Redis Fallback**: If Redis is offline or restarting, the route dynamically imports `processJobLocal` from `@/lib/worker` and executes the task asynchronously in the Node runtime without blocking the HTTP response thread.

## Module 2: Queue & Redis Subsystem
**File Path**: [`lib/queue.ts`](file:///c:/Projects/secure-pr/lib/queue.ts)

### 2.1 Why It Is Used
Webhooks arrive unpredictably in bursts. The queue subsystem buffers incoming PR audit requests, manages job state persistence, controls concurrency, enforces retries with exponential backoff, and cleans up completed/failed jobs.

### 2.2 How It Works Internally

```typescript
import { Queue } from 'bullmq';
import IORedis from 'ioredis';

const redisUrl = process.env.UPSTASH_REDIS_URL || 'redis://localhost:6379';

export const redisConnection = new IORedis(redisUrl, {
  maxRetriesPerRequest: null,
  enableReadyCheck: false,
  retryStrategy: (times) => Math.min(times * 500, 5000),
});

export const prReviewQueue = new Queue('pr-review', {
  connection: redisConnection,
  defaultJobOptions: {
    attempts: 3,
    backoff: { type: 'exponential', delay: 5000 },
    removeOnComplete: { count: 200 },
    removeOnFail: { count: 100 },
  },
});
```

#### Key Technical Configurations:
1. **`maxRetriesPerRequest: null`**: BullMQ requires `ioredis` to operate with `maxRetriesPerRequest` set to `null` so that command retries are managed by BullMQ's internal queue mechanics rather than failing connection attempts prematurely.
2. **`enableReadyCheck: false`**: Avoids blocking initialization delays when connecting to managed Redis instances (such as Upstash or Redis Enterprise).
3. **`retryStrategy`**: Reconnects with progressive delays (500ms, 1000ms... capped at 5000ms) to ensure resilience against momentary network blips.
4. **Exponential Backoff**: If an LLM call or GitHub API request fails (e.g. rate limit error 429), BullMQ automatically retries up to 3 times, delaying execution exponentially (5s, 10s, 20s).
5. **Memory Management**: Keeps the 200 most recent completed jobs and 100 failed jobs in Redis to avoid unbounded memory growth.

## Module 3: AI Security Auditor Core
**File Path**: [`lib/gemini.ts`](file:///c:/Projects/secure-pr/lib/gemini.ts)

### 3.1 Why It Is Used
This module encapsulates the core intelligence of DevInsight. It interfaces with Groq's high-speed inference engine (`llama-3.3-70b-versatile`) to perform automated static application security testing (SAST) on git patches.

### 3.2 How It Works Internally

#### System Prompt Engineering & Threat Classification
The module defines a strict system prompt targeting 7 threat categories:

1. **SQL Injection**: Unparameterized queries, string interpolation in SQL strings.
2. **Hardcoded Secrets**: Embedded API keys, private tokens, passwords, credentials.
3. **Insecure Dependencies**: Known-vulnerable package versions and dangerous imports.
4. **Cross-Site Scripting (XSS)**: Unsanitized dynamic input in HTML/JS rendering contexts.
5. **Path Traversal**: Unsanitized user-controlled file paths.
6. **Broken Authentication**: Missing auth checks, weak token verification, insecure sessions.
7. **Sensitive Data Exposure**: Logging credentials, PII, or internal stack traces to clients.

#### Code Implementation & Safety Controls

```typescript
const GROQ_MODEL = 'llama-3.3-70b-versatile';
const MAX_DIFF_CHARS = 50_000;
const MAX_RETRIES = 2;
const RETRY_DELAY_MS = 2000;

let _client: Groq | null = null;

function getClient(): Groq {
  if (!_client) {
    const apiKey = process.env.GROQ_API_KEY;
    if (!apiKey) throw new Error('GROQ_API_KEY environment variable is not set');
    _client = new Groq({ apiKey });
  }
  return _client;
}

export async function auditDiff(diff: string): Promise<string> {
  const truncated =
    diff.length > MAX_DIFF_CHARS
      ? diff.slice(0, MAX_DIFF_CHARS) + '\n\n*(diff truncated at 50k chars)*'
      : diff;

  const client = getClient();
  let lastError: Error | null = null;

  for (let attempt = 0; attempt <= MAX_RETRIES; attempt++) {
    try {
      const completion = await client.chat.completions.create({
        model: GROQ_MODEL,
        temperature: 0.2,
        max_tokens: 2048,
        messages: [
          { role: 'system', content: SYSTEM_PROMPT },
          {
            role: 'user',
            content: `Audit the following PR diff for security vulnerabilities:\n\n\`\`\`diff\n${truncated}\n\`\`\``,
          },
        ],
      });
      return completion.choices[0]?.message?.content ?? '> ✅ No response from model.';
    } catch (err) {
      lastError = err instanceof Error ? err : new Error(String(err));
      if (attempt < MAX_RETRIES) await sleep(RETRY_DELAY_MS * (attempt + 1));
    }
  }
  throw lastError!;
}
```

#### Key Mechanics:
- **Singleton Client Pattern**: The `Groq` SDK client is lazily initialized and reused (`_client`), avoiding allocation overhead on every audit.
- **Diff Truncation Barrier**: Git diffs exceeding 50,000 characters are safely truncated to prevent prompt overflow errors and manage token usage.
- **Low Temperature (`0.2`)**: Controls token sampling to favor deterministic, reproducible security findings while reducing hallucinations.
- **Retry Logic with Linear Backoff**: Catches rate limit errors or socket disconnects, retrying up to 2 times with scaling delays.

#### GitHub Diff Fetching & Comment Posting
- Uses Octokit REST client authenticated via `GITHUB_TOKEN`.
- Fetches diff using media type header `mediaType: { format: 'diff' }`, retrieving raw unified git patch output.
- Posts comments directly to the PR issue thread (`octokit.issues.createComment`).

```typescript
async function fetchPRDiff(owner: string, repo: string, prNumber: number): Promise<string> {
  const octokit = getOctokit();
  const response = await octokit.pulls.get({
    owner,
    repo,
    pull_number: prNumber,
    mediaType: { format: 'diff' },
  });
  return response.data as unknown as string;
}
```

#### Finding Parser & Severity Normalizer
The worker parses raw LLM markdown outputs to construct telemetry objects:
```typescript
function parseAuditReport(markdown: string) {
  const findings: Array<{ severity: 'critical' | 'high' | 'medium' | 'low'; type: string }> = [];
  const lines = markdown.split('\n');
  
  for (const line of lines) {
    const trimmed = line.trim();
    if (trimmed.startsWith('### [')) {
      const match = trimmed.match(/^###\s+\[([^\]]+)\]\s+(.+)$/);
      if (match) {
        const sevText = match[1].toLowerCase();
        let severity: 'critical' | 'high' | 'medium' | 'low' = 'low';
        if (sevText.includes('critical') || sevText.includes('🔴')) severity = 'critical';
        else if (sevText.includes('high') || sevText.includes('🟠')) severity = 'high';
        else if (sevText.includes('medium') || sevText.includes('🟡')) severity = 'medium';
        else if (sevText.includes('low') || sevText.includes('🔵')) severity = 'low';

        const rawType = match[2].trim();
        const type = normalizeBugType(rawType);
        findings.push({ severity, type });
      }
    }
  }

  let status: 'critical' | 'warning' | 'clean' = 'clean';
  if (findings.some(f => f.severity === 'critical')) status = 'critical';
  else if (findings.some(f => f.severity === 'high' || f.severity === 'medium')) status = 'warning';

  return { status, bugsCount: findings.length, bugTypes: findings.map(f => f.type) };
}
```

## Module 5: Dual-Layer Database Subsystem
**File Path**: [`lib/db.ts`](file:///c:/Projects/secure-pr/lib/db.ts)

### 5.1 Why It Is Used
The database module persists security audit logs, execution timing, vulnerability metadata, and regional tags. It features a dual-layer architecture with transparent failover between Redis and a local JSON file store (`lib/audits-db.json`).

### 5.2 How It Works Internally

```typescript
function isRedisReady(): boolean {
  return redisConnection.status === 'ready';
}

export async function storeAudit(audit: any): Promise<void> {
  const auditStr = JSON.stringify(audit);

  if (isRedisReady()) {
    try {
      await redisConnection.lpush('devinsight:audits', auditStr);
      await redisConnection.ltrim('devinsight:audits', 0, 999);
      return;
    } catch (err) {
      console.error('Failed to save to Redis, falling back to local file:', (err as Error).message);
    }
  }

  // Fallback to local JSON file database
  try {
    let audits = [];
    if (fs.existsSync(DB_FILE)) {
      const content = fs.readFileSync(DB_FILE, 'utf8');
      audits = JSON.parse(content);
    }
    audits.unshift(audit);
    if (audits.length > 1000) audits = audits.slice(0, 1000);
    fs.writeFileSync(DB_FILE, JSON.stringify(audits, null, 2), 'utf8');
  } catch (err) {
    console.error('Failed to save audit to local JSON file:', (err as Error).message);
  }
}
```

#### Dual-Layer Mechanism:
1. **Primary (Redis List `devinsight:audits`)**:
   - Stores audit records as serialized JSON strings.
   - `LPUSH` inserts new logs at the head of the list.
   - `LTRIM devinsight:audits 0 999` caps the database at 1,000 logs in `O(1)` time.
2. **Secondary (Local JSON File `lib/audits-db.json`)**:
   - Used when Redis is unreachable.
   - Reads existing records, prepends new log, caps at 1,000 items, and writes atomically.

services:
  redis:
    image: redis:alpine

#### Multi-Stage Next.js Build (`Dockerfile`)
1. **Stage 1 (`deps`)**: Runs `npm ci --omit=dev` to isolate production dependencies.
2. **Stage 2 (`builder`)**: Installs full devDependencies and runs `npm run build` to generate standalone Next.js build output.
3. **Stage 3 (`runner`)**: Uses `node:20-alpine`, runs as an unprivileged system user (`nextjs:1001`), and launches `node server.js` exposing port 3000.

#### Worker Container (`worker.Dockerfile`)
Installs `tsx` globally and launches `node --import tsx/esm worker.mjs` to execute TypeScript worker modules directly in ESM mode.
